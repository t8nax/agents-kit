# Раскладка базы знаний

Что лежит в базе и по каким правилам туда пишут. Память задачи — `task-memory.md` рядом, запись бэклога — `backlog-record.md` рядом. Каркас заводит `base-init.ps1`. Файлы базы этих правил не повторяют.

```
<база>/
  agents-kit.json
  .gitignore        local/
  product.md
  boundaries.md
  flow.md
  backlog.md
  decisions/<область>.md
  agents/<имя субагента>.md
  work/<слаг пути копии>.md
  local/            значения кредов, вне git
```

**Хук подаёт содержимым `product.md` и `boundaries.md` и только их; из `decisions/` — оглавление: каждый файл и его строку `когда:`.** Подаваемый файл приезжает в каждую сессию целиком. Остальное сессия читает сама, когда нужно.

**HTML-комментарии до сессии не доходят:** хук вырезает их. Правило, спрятанное в `<!-- -->`, не действует.

## Что попадает в базу

Тест входа для строки знания: **убери её — начнёт ли сессия ошибаться?** Не начнёт — строки быть не должно. Выводимое из кода в базу не пишется.

Строка, верная только вместе с числом из кода — версией, портом, значением настройки, — **идёт в базу без числа:** ограничение и причина. «Держать `Microsoft.OpenApi` на ветке 2.x, потому что 3.x ломает сборку» — знание; «сейчас 2.12.2» — `csproj`.

Секреты — инвариант «Секреты не попадают в git базы».

## Куда именно

Файлы знания правятся по месту.

| Файл | Вопрос | Проверка строки | Потолок |
|---|---|---|---|
| `product.md` | что за система и зачем | перепиши проект на другом стеке — строка останется верной | 50 строк |
| `boundaries.md` | чего агенту нельзя и кто решает | убери строку — агент решит это сам, хотя решать не ему | 30 строк |
| `decisions/<область>.md` | как договорились делать эту область системы и почему | строка умирает вместе с тем, о чём она | — |

Пустой `boundaries.md` законен: на проекте действуют одни инварианты кита.

Потолок считает непустые строки без HTML-комментариев; перерасход — красная находка сверки. Упёрся подаваемый файл в потолок — это не повод поднять потолок, а признак, что в нём лежит не прошедшее тест входа.

Имя проекта — заголовок `product.md`: `# Order Service — продукт`, как проект называет команда, а не имя каталога. Хук берёт его отсюда в шапку подачи.

Части системы в `product.md` называются по роли — API, веб-клиент, база. Чем они сделаны — решение, и живёт оно в `decisions/`.

**Один факт — один файл.** Тянет в два — у файлов разные вопросы к предмету, и в каждый идёт свой ответ, а не копия.

## Флоу проекта

Кит флоу не пишет: каркас — файл без стадий, стадии пишет проект с оператором. Потолка у флоу нет.

### Стадия

Стадии идут в порядке исполнения, номера подряд с 1. Стадия — заголовок с номером и названием, под ним подряд пары `ключ: значение`, после пустой строки — описание.

Описание пишется свободным текстом, но не сплошной прозой: абзацы — через пустую строку, перечень и порядок действий — списком (`-`, `1.` или пунктами `3.1.`, `3.2.`). Одна мысль — один абзац или пункт.

**Ссылка на другую стадию — слово «стадия» и её название в кавычках:** «дифф, собранный в стадии «Сборка»». Номером стадия не адресуется. Красные находки сверки — ссылка номером, ссылка на название, которого во флоу нет, и две стадии с одним названием.

```markdown
## 3. Ревью

исполнитель: reviewer
выход: вердикт по sha проверенного коммита, записанный оркестратором в память
пропуск: правка только в текстах
возврат: замечания — стадия «Сборка»

3.1. Собрать дифф всей ветки задачи.
   Ревью идёт по диффу всей ветки, а не по последнему коммиту: правка
   прошлого круга иначе уходит непроверенной.
3.2. Отдать дифф ревьюеру.
3.3. Разобрать замечания.
   3.3.1. Исправить в том же круге.
   3.3.2. Что не исправлено — вопросом оператору.
```

Ключи — закрытый перечень; своих не заводят.

| Ключ | Значение | Обязателен |
|---|---|---|
| `исполнитель` | `оркестратор` · `оператор` · `<имя субагента>` | да |
| `помощники` | имена субагентов через запятую, как в их поле `name:` | нет |
| `выход` | что предъявить: коммит, строка в памяти, вывод прогона | да |
| `пропуск` | условие, при котором стадия не проходится | нет |
| `возврат` | `<условие> — стадия «<название>»`; строка на каждый возврат | нет |

- **`выход` — главное в стадии.** «Убедиться», «обдумать» выходом не бывают.
- **`исполнитель` — чья работа даёт выход стадии.** Подготовить ему вход и записать выход — ведение флоу, и оно на оркестраторе всегда.
- **`оркестратор`** — работу стадии делает сама сессия `/drive`.
- **`<имя субагента>`** — как в его поле `name:`; где он живёт и как попадает в рабочую копию — раздел «Субагенты проекта». Задание ему — описание стадии; результат в базу записывает оркестратор, и выход звучит как «субагент вернул → оркестратор записал». Субагента не видно и в базе его нет — вопрос оператору; стадию за субагента сессия не проходит.
- **`оператор`** — только то, чего сессия не может. Выход — сделанное оператором («смержено: <sha>»), а не просьба. Пока выхода нет, в «Оператору» памяти стоит вопрос.
- **`помощники`** — кого оркестратор зовёт на кусок своей работы в стадии: `помощники: test-runner, code-explorer`. Ключ стоит только при `исполнитель: оркестратор`. Что помощник получает и что возвращает — пунктом описания; названного помощника не видно — как исполнителя.
- **`пропуск` не указан** — стадия проходится всегда. Пропущенная по условию стадия оставляет в «Агенту → Флоу» памяти строку, почему.
- **`возврат`** — условие, при котором работа после стадии идёт не дальше, а к названной стадии. Строка на каждый возврат; названная стадия стоит во флоу раньше. Сбылось несколько условий — идёт первый по порядку строк. Возврат задаёт только этот ключ: упоминание стадии в описании остаётся ссылкой. Красные находки сверки — возврат без условия, без названия стадии в кавычках, на стадию, которой во флоу нет, и на стадию не раньше этой.
- **Описание** говорит, как стадия проходится на этом проекте; решение о порядке работы пишется вместе с причиной.

Во флоу нет устройства системы (`product.md`, `decisions/`), значений команд, портов и кредов (там, где их читает код; креды — `local/`) и инвариантов кита: инвариант действует и без стадии о нём.

Флоу правится явной правкой по месту. Работа разошлась с флоу — вопрос оператору, а не молчаливое отступление.

## Когда параллельные задачи сходятся

Мержа среди этих мест нет ни одного.

- **Память не сходится:** у каждой копии свой файл, и умирает он со своей задачей.
- **Знание сходится в общих файлах базы.** База — один каталог на все сессии: соседняя правит те же файлы на диске, рядом лежит её незакоммиченная работа. Файлы знания и `backlog.md` правятся **по месту и точечно**, а коммит — явными путями.
- **Код сходится в репозитории проекта,** и база об этом не знает.

## Решения

**Один файл `decisions/` — одна область:** форма API, тесты фронта, развёртывание. Каталог плоский, имя файла — слаг области.

```markdown
# <чего касаются решения>
когда: <какие задачи их касаются>

## <тема>
- <решение и почему>
```

- **Строка `когда:` обязательна** и одна, в начале файла. Без неё файла нет в оглавлении — красная находка сверки.
- **`когда:` называет задачи, а не тему.** «правка эндпоинтов и контрактов API» — да; «про API» — нет.

Потолок файла решений — 40 строк. Упёрся — в файле две области, и он режется на два.

### Когда решения читаются

- **Задача взята и критерий записан** — прочитать решения по инварианту «Решения проекта читаются до первой стадии флоу» и записать файлы строкой `Решения:` памяти.
- **Работа задела решения, которых в строке нет,** — прочитать до изменения и дописать в строку.
- **Сомнение, касается ли файл задачи,** решается чтением.

### Свод, а не журнал

- Раздел файла — тема (`## Кэш`). Новое решение **заменяет прежнее по тому же адресу**, а не дописывается снизу.
- Решения без своего файла заводят новый со строкой `когда:`, а не дописываются в чужую область.
- Строка — что делаем и почему; отброшенные варианты не пишутся, «как было» живёт в истории git базы.
- **Строка живёт, пока жива причина.** Обход починенной ошибки, ловушка ушедшего окружения уходят тем же коммитом, что фиксирует заменившее их знание.

## Субагенты проекта

Субагентов, которых зовёт флоу, база держит у себя — `agents/<имя>.md`, каталог плоский. В рабочую копию их довозит `agents-deploy.ps1`: кладёт файл в `<рабочая копия>/.claude/agents/` и прячет его от git проекта. Правится файл базы, а лежащее в копии — производная: правка в ней уезжает следующим прогоном.

- **Имя файла — строка `name:` субагента,** и этим же именем зовёт его флоу. Нет `name:` или разошлось с именем файла — красная находка сверки.
- **Файл — субагент Claude Code как он есть:** кит его не разбирает и полей, кроме `name:`, не знает.
- **Сессия довозит его двумя моментами:** субагент записан или поправлен в базе — тут же в свою копию; сверка назвала расхождение. Связывание копии и заведение новой рабочей копии довозят сами.
- **Названного флоу субагента не видно, а в базе он есть** — довезти и сказать оператору, с какой сессии его звать.
- **Довезённый виден со следующей сессии** — набор субагентов сессия собирает при запуске. Оператору говорится, с какой сессии его звать.
- **Отслеживаемый git файл копии скрипт не трогает:** занятое имя он называет, разводит имена оператор.
- Субагент, которого зовут все проекты, в базе не нужен: набор профиля оператора и субагенты плагинов видны и так.

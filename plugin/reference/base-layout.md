# Раскладка базы знаний

Что лежит в базе и по каким правилам туда пишут. Флоу — сценарии и этапы — `flow-stages.md` рядом, память задачи — `task-memory.md` рядом, запись бэклога — `backlog-record.md` рядом. Каркас, папку оператора и личный репозиторий заводит `base-init.ps1`. Файлы базы этих правил не повторяют.

```
<база>/
  agents-kit.json
  .gitignore        local/
  product.md
  team.md
  tracker.md        если у проекта есть трекер задач
  decisions/<область>.md
  artifacts/<имя файла>
  people/<имя оператора>/   выложенное для коллег
    flow/
      scenarios.md
      stages/<слаг>.md
    agents/<имя субагента>.md
  local/            вне git базы
    me.json         список копий этой машины и имя её оператора
    me/             личный репозиторий оператора, свой git
      autonomy.md
      flow/
        scenarios.md
        stages/<слаг>.md
      agents/<имя субагента>.md
      backlog.md
      work/<машина>/<слаг пути копии>.md
      work/<машина>/<слаг пути копии>/flow/   флоу задачи
      artifacts/<имя файла>
    <значения кредов>
```

## Оператор

Общая база — знание и папки операторов в `people/`: это видят все, кто ведёт проект. Своё у каждого оператора — личный репозиторий `local/me/`: рамки агента, флоу, субагенты, бэклог, память задач и их артефакты; агент оператора работает только по ним. Папка `people/<имя>/` держит флоу и субагентов, которых оператор выложил для коллег, — раздел «Выложить и взять флоу» `flow-stages.md`; она есть и пустой. Одиночный проект раскладывается так же: оператор в `people/` один.

- **Имя оператора** — латиница в нижнем регистре, цифры и дефис между ними: `b-ignatyev`, `boris`. Спрашивается у оператора; черновик — инициал и фамилия из `git config user.name`: `Boris Ignatyev` → `b-ignatyev`. Имя берётся по свежей базе: папка `people/<имя>/` уже есть — спросить оператора, его ли она; не его — другое имя.
- **Личный репозиторий** заводится вместе с именем. Есть у оператора приватный remote для него — спросить адрес: тогда репозиторий приезжает клоном, и всё в нём сходится между его машинами — раздел «Когда параллельные задачи сходятся».
- Заводит оба `base-init.ps1 -Path <база> -Operator <имя> [-Remote <адрес>]` — один раз на машину; имя хранится в `local/me.json`.
- Сессия в `people/` не пишет: свою папку заводит `base-init.ps1`, выложенное в неё пишет `flow-share.ps1`. Папки в `people/` сверка не судит, а своей без флоу — называет.
- **Требования команды к любому флоу** — «без ревью не мержим» — пишутся в `team.md`, а не во флоу или рамки одного оператора.

**Хук называет путями `product.md` и `team.md` базы и `autonomy.md` личного репозитория этой машины и только их — сессия читает их первым делом; из `decisions/` он подаёт оглавление: каждый файл и его строку `когда:`.** Названный хуком файл каждая сессия читает целиком. Остальное сессия читает сама, когда нужно.

**HTML-комментарии — подсказки шаблона, а не знание:** правило, спрятанное в `<!-- -->`, не действует.

## Что попадает в базу

Тест входа для строки знания: **убери её — начнёт ли сессия ошибаться?** Не начнёт — строки быть не должно. Выводимое из кода в базу не пишется.

Строка, верная только вместе с числом из кода — версией, портом, значением настройки, — **идёт в базу без числа:** ограничение и причина. «Держать `Microsoft.OpenApi` на ветке 2.x, потому что 3.x ломает сборку» — знание; «сейчас 2.12.2» — `csproj`.

Секреты — инвариант «Секреты не попадают в git базы».

## Куда именно

Файлы знания правятся по месту.

| Файл | Вопрос | Проверка строки | Потолок |
|---|---|---|---|
| `product.md` | что за система и зачем | перепиши проект на другом стеке — строка останется верной | 50 строк |
| `team.md` | чего нельзя любому агенту проекта, кто бы его ни вёл | убери строку — агент коллеги сделает то, что команда запретила | 30 строк |
| `autonomy.md` | что агент решает сам, а чего ему нельзя без этого оператора | убери строку — агент решит это сам, хотя решать не ему | 30 строк |
| `tracker.md` | где задачи команды и чем к ним ходить | убери строку — сессия не возьмёт задачу из трекера или не заведёт в нём задачу | — |
| `decisions/<область>.md` | как договорились делать эту область системы и почему | строка умирает вместе с тем, о чём она | — |

Пустые `team.md` и `autonomy.md` законны: действуют одни инварианты кита.

Потолок считает непустые строки без HTML-комментариев; перерасход — красная находка сверки. Упёрся подаваемый файл в потолок — это не повод поднять потолок, а признак, что в нём лежит не прошедшее тест входа.

Имя проекта — заголовок `product.md`: `# Order Service — продукт`, как проект называет команда, а не имя каталога. Хук берёт его отсюда в шапку подачи.

Части системы в `product.md` называются по роли — API, веб-клиент, база. Чем они сделаны — решение, и живёт оно в `decisions/`.

**Один факт — один файл.** Тянет в два — у файлов разные вопросы к предмету, и в каждый идёт свой ответ, а не копия.

## Трекер

`tracker.md` описывает трекер проекта. Файла нет — трекера у проекта нет. Проект ведут двое и больше — общие задачи живут в трекере: общего бэклога у команды нет.

Заводит и правит файл скилл `tracker`. В трекер сессия ходит инструментом, подключённым у оператора. Файл — разделы с этими заголовками, внутри раздела — слова, а `## Где задачи` начинается строками трекера, сервера и проекта — ниже:

| Раздел | Что в нём |
|---|---|
| `## Где задачи` | строки `трекер:`, `сервер:`, `проект:`; под ними словами — каким инструментом ходить — MCP-сервер, `gh`, CLI трекера, кредов в файле нет — инвариант «Секреты не попадают в git базы»; доска или фильтр, если нужны; у трекера не из таблицы трекеров — вид номера задачи |
| `## Показ бэклога` | как найти задачи, назначенные на оператора |
| `## Взятие задачи` | что значит, что задача уже в работе, и что изменить в задаче трекера: назначить на себя, перевести в работу — статус, метка, колонка, — оставить комментарий |
| `## Задача закрыта` | что изменить в задаче трекера: статус, комментарий с результатом — или ничего, когда её меняет мерж |
| `## Вынос записи бэклога` | как завести задачу: куда и с какими полями |

Над разделами — заголовок `# <имя проекта> — трекер`.

Раздел `## Где задачи` начинается тремя строками, каждая по одному разу, за ними пустая строка и слова:

```markdown
## Где задачи

трекер: YouTrack
сервер: https://yt.acme.local
проект: PAY

Ходим MCP-сервером youtrack.
```

- **`трекер:`** — имя из таблицы трекеров, регистр не важен; скилл `tracker` пишет его, как в таблице.
- **`сервер:`** — адрес вида `http(s)://хост[:порт][/путь]` без логина, пароля, запроса и фрагмента. У GitHub тоже: `https://github.com` или адрес Enterprise.
- **`проект:`** — один, по шаблону проекта своего трекера из таблицы.

| Трекер | Проект | Шаблон проекта | Номер задачи |
|---|---|---|---|
| `GitHub` | владелец и репозиторий через `/` | `[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+` | `#<число>` |
| `GitLab` | группа, подгруппы и проект через `/` | `[A-Za-z0-9_.-]+(/[A-Za-z0-9_.-]+)+` | `#<число>` |
| `Jira` | ключ проекта | `[A-Z][A-Z0-9_]+` | `<проект>-<число>` |
| `YouTrack` | ID проекта | `[A-Za-z][A-Za-z0-9_]*` | `<проект>-<число>` |

Шаблон проекта — регулярное выражение на значение целиком, с учётом регистра. Трекера нет в таблице — проект у него любой непустой, а вид номера задачи пишется словами раздела.

Нет раздела, раздел пуст и раздел не из таблицы разделов — красная находка сверки. Строки трекера, сервера или проекта нет, она пуста или повторена, сервер не адрес этого вида или несёт логин, пароль, запрос, фрагмент, проект не по шаблону — тоже красная; трекер не из таблицы трекеров — предупреждение.

**В трекер не пройти** — в трекере в этот момент сессия ничего не делает и говорит оператору, что не так:

- `tracker.md` нет, а оператор назвал задачу трекера или просит вынести в него запись, — предложить завести трекер скиллом `tracker`;
- нужного раздела нет или он пуст — предложить поправить трекер скиллом `tracker`;
- в `## Где задачи` нет строки трекера, сервера или проекта, какая-то пуста или сверка назвала на них красную находку — предложить поправить трекер скиллом `tracker`. Трекер не из таблицы трекеров в трекер пускает;
- инструмента нет или трекер недоступен — сказать, что подключить, а на закрытии задачи — что изменить в ней руками.

Правило вне этих разделов — «комментарий в задачу после каждого этапа» — порядок работы, и пишется оно во флоу.

У задачи одно место: командная — в трекере, личная — в бэклоге. Задача трекера называется именем трекера и номером — `backlog-record.md`, «Номер». Как берут задачу из трекера — `drive`, как выносят в него запись бэклога — `backlog-record.md`, «Вынести в трекер».

## Когда параллельные задачи сходятся

- **Память не сходится:** у каждой копии на каждой машине свой файл в личном репозитории, и умирает он со своей задачей. Память другой машины сверка не судит.
- **На машине знание сходится в общих файлах базы, бэклог — в личном репозитории.** База — один каталог на все сессии машины: соседняя правит те же файлы на диске, рядом лежит её незакоммиченная работа. Файлы знания и `backlog.md` правятся **по месту и точечно**, а коммит — явными путями, каждый в свой репозиторий.
- **Между машинами база и личный репозиторий сходятся через свой `origin`.** Сводит `sync.ps1` скриптов кита: `-Repo Base` или `-Repo Personal`, `-Action Pull` — забрать, `-Action Push` — забрать и отдать; когда — говорят скиллы. Нет `origin` — репозиторий живёт на машине, и сводить не с чем.
- **Код сходится в репозитории проекта,** и база об этом не знает.

Что делать по выводу `sync.ps1`:

- **Забрано** — вывод называет пришедшие файлы. Среди них уже прочитанные сессией — перечитать.
- **Remote недоступен, не отдано** — сказать оператору и работать с локальным: отдастся при следующем сведении.
- **Не забрано из-за незакоммиченной правки** — её ведёт соседняя сессия: сказать оператору и работать дальше, заберётся при следующем сведении.
- **Пришла база другого формата** — работа со знанием остановлена: сказать оператору и открыть новую сессию; что делать, скажет она.
- **Конфликт** — сведение стоит недоделанным, и работа со знанием остановлена до разрешения. Сводится файл за файлом, вопрос оператору — в разговоре:
  - `backlog.md` — без вопроса, по `backlog-record.md`, «Номер»; запись, поправленная с обеих сторон, — вопрос;
  - двоичный файл — артефакт — спросить оператора, чью редакцию оставить, и передать ответ команде ключом `-Keep <путь>=Remote` или `-Keep <путь>=Local`;
  - остальное — показать оператору обе редакции его словами и спросить, какая верна или как их соединить; записать ответ в файл без меток конфликта.

  Затем команда из вывода с `-Action Continue` — базу она и отдаёт, личный репозиторий отдаётся в свой момент — и новая сессия.

Коммиты памяти не отдаются по одному: они уезжают со следующим отданием личного репозитория.

## Решения

**Один файл `decisions/` — одна область:** форма API, тесты фронта, развёртывание. Каталог плоский, имя файла — слаг области.

```markdown
# <чего касаются решения>
когда: <какие задачи их касаются>

## <тема>
- <решение и почему>
```

- **Строка `когда:` обязательна** и одна, в начале файла. Без неё файла нет в оглавлении — красная находка сверки.
- **`когда:` называет задачи, а не тему.** «правка эндпоинтов и контрактов API» — да; «про API» — нет.

Потолок файла решений — 40 строк. Упёрся — в файле две области, и он режется на два.

### Когда решения читаются

- **Задача взята** — прочитать решения по инварианту «Решения проекта читаются до первого этапа сценария» и записать файлы строкой `Решения:` памяти.
- **Работа задела решения, которых в строке нет,** — прочитать до изменения и дописать в строку.
- **Сомнение, касается ли файл задачи,** решается чтением.

### Свод, а не журнал

- Раздел файла — тема (`## Кэш`). Новое решение **заменяет прежнее по тому же адресу**, а не дописывается снизу.
- Решения без своего файла заводят новый со строкой `когда:`, а не дописываются в чужую область.
- Строка — что делаем и почему; отброшенные варианты не пишутся, «как было» живёт в истории git базы.
- **Строка живёт, пока жива причина.** Обход починенной ошибки, ловушка ушедшего окружения уходят тем же коммитом, что фиксирует заменившее их знание.

## Субагенты проекта

Субагентов, которых зовут этапы, держит личный репозиторий — `local/me/agents/<имя субагента>.md`, каталог плоский. В рабочую копию `agents-deploy.ps1` довозит субагентов её оператора: кладёт файл в `<рабочая копия>/.claude/agents/` и прячет его от git проекта. Правится файл личного репозитория, а лежащее в копии — производная: правка в ней уезжает следующим прогоном. Выложенные в `people/` не довозятся. Субагентов видит только Claude Code: в сессии Codex их нет.

- **Имя файла — строка `name:` субагента,** и этим же именем зовёт его этап. Нет `name:` или разошлось с именем файла — красная находка сверки.
- **Файл — субагент Claude Code как он есть:** кит его не разбирает и полей, кроме `name:`, не знает.
- **Сессия довозит его двумя моментами:** субагент записан, поправлен или взят с флоу коллеги — тут же в свою копию; сверка назвала расхождение. Связывание копии и заведение новой рабочей копии довозят сами.
- **Названного этапом субагента не видно, а в личном репозитории он есть** — довезти и сказать оператору, с какой сессии его звать.
- **Довезённый виден со следующей сессии** — набор субагентов сессия собирает при запуске. Оператору говорится, с какой сессии его звать.
- **Отслеживаемый git файл копии скрипт не трогает:** занятое имя он называет, разводит имена оператор.
- Субагент, которого зовут все проекты, в личном репозитории не нужен: набор профиля оператора и субагенты плагинов видны и так.

## Артефакты

Файлы артефактов держит `artifacts/` того репозитория, чей файл на них ссылается: общей базы — для файлов знания, личного репозитория — для его файлов: рамок, флоу, бэклога и памяти задач. Снимок экрана, лог, выгрузка, макет, документ, который дал этап. Каталог плоский; имя файла говорит, что в нём, — `ORD-12-макет-корзины.png`, без пробелов. Имя занято — берётся другое, чужой файл не перезаписывается.

- **Ссылка на файл — его путь от корня своего репозитория `artifacts/<имя>`** в любом `.md` этого репозитория: записи бэклога, памяти задачи, файле решений. Ссылка в HTML-комментарии не считается. Ссылка из личного репозитория общий артефакт не держит, и наоборот.
- **Файл живёт, пока на него есть ссылка.** Правка, которая убирает последнюю ссылку, — закрытие задачи, удаление записи бэклога, правка файла — тем же коммитом удаляет файл `git rm`. Файл нужен и после неё — ссылка на него идёт туда, где у неё своя причина жить: в запись бэклога о том, что с ним сделать, или в файл знания; файлу знания артефакт копируется в `artifacts/` базы.
- **Документ, переживший задачу, на фиксации переносится строками** в `decisions/` или `product.md`. Файлом со ссылкой из них остаётся только то, что строками не перескажешь: макет, схема.
- **Потолок артефакта — 5 МБ.** Крупнее в базу не кладётся: артефактом становится внешний адрес — диск, трекер.
- **Снимок, на котором виден секрет, в базу не кладётся** — инвариант «Секреты не попадают в git базы».

Файл больше потолка и коммит, после которого на лежащий файл `artifacts/` не ссылается ни один `.md` его репозитория, — красная находка сверки. Подкаталог в `artifacts/`, файл без ссылок и ссылка на файл, которого нет, — предупреждение.

## Список копий

Список копий — поле `workspaces` в `local/me.json`, у каждой машины свой, и пишет его `link.ps1`; второго списка в базе нет. Копию, склонированную на другой машине, связывают там заново.

Номер формата базы — поле `version` в `agents-kit.json`, буквы номеров бэклога — поле `prefix`: их ставит `base-init.ps1` новой базе, номер поднимает `base-migrate.ps1` при переводе.

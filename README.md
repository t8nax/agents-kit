# agents-kit

Агентский кит для Claude Code: **инженерную работу ведёт агент, а оператор вступает там, где агент не может**.

Знание проекта — что за система, где граница решений агента, какие решения действуют — живёт **отдельным репозиторием базы знаний**, вне кода и вне кита. Сессия находит базу по указателю в git config рабочей копии и с первой секунды получает её знание вместе с инвариантами кита.

## Как связаны основная копия и база

Связь двусторонняя, обе стороны обязательны.

| Сторона | Где лежит |
|---|---|
| указатель репозитория | `agents-kit.base` в локальном git config копии |
| указатель каталога | `agents-kit.<путь от корня>.base` там же |
| список копий | `agents-kit.json` в корне базы |

Каталогом под кит берут, например, модуль монорепы. Сессия берёт ближайший связанный каталог над собой, а нет такого — указатель репозитория.

## Установка

**Каталог автозагрузки — для того, кто кит правит.** Ссылка на клон в `~/.claude/skills/`: кит грузится прямо из клона, без установки и без версий.

```powershell
New-Item -ItemType Junction -Path "$env:USERPROFILE\.claude\skills\agents-kit" -Target <клон кита>
```

**Маркетплейс — для того, кто китом пользуется.**

```powershell
claude plugin marketplace add <клон или github-репозиторий>
claude plugin install agents-kit@agents-kit
```

Оба способа сразу не включать.

## Обновление

**Поставленный каталогом автозагрузки** обновляется `git pull` в клоне. Правка действует со следующей сессии, а в открытой — после `/reload-plugins`; версия в этом не участвует.

**Поставленный маркетплейсом** копируется в кэш плагинов, и копия меняется только со сменой номера версии. У сторонних маркетплейсов автообновление выключено по умолчанию — включается один раз в `/plugin` → **Marketplaces** → `agents-kit`. Иначе обновление идёт руками, и маркетплейс обновляется отдельно от плагина:

```powershell
claude plugin marketplace update agents-kit
claude plugin update agents-kit@agents-kit
```

Автообновление срабатывает после старта сессии с задержкой до десяти минут: открытая сессия доигрывает на прежней версии, свежую берёт следующая.

**Что говорит номер.** Сменился средний разряд (`0.X.0`) — после обновления нужна работа руками, и в чём база разошлась с новым форматом, назовёт сверка базы в первой же сессии. Сменился последний (`0.x.Y`) — обновиться и пользоваться.

## Связать проект с базой

Сначала база — каталог рядом с рабочими копиями, вне них, с именем вида `<проект>-knowledge`:

```powershell
pwsh -NoProfile -File <клон кита>\scripts\base-init.ps1 -Path <каталог базы> -Name "<имя проекта>"
```

Скрипт раскладывает каркас с именем проекта в заголовках (без `-Name` — имя каталога) и заводит репозиторий; повторный прогон заполненного не трогает и довозит недостающее. Что за файлы — [reference/base-layout.md](reference/base-layout.md).

Дальше из основной копии:

```powershell
pwsh -NoProfile -File <клон кита>\scripts\link.ps1 -Base <каталог базы>
```

Команда пишет обе стороны. Под кит идёт один каталог репозитория — та же команда с `-Scope Directory`, запущенная в нём. Вторая основная копия проекта связывается так же; `git worktree` связывать не нужно — он приводится к основной копии. Без аргументов скрипт показывает, как связано сейчас, и называет связанные каталоги репозитория, — первая диагностика при разрыве и при молчании кита.

`/onboard` — те же шаги из открытой в проекте сессии: скилл заводит базу, связывает копию и заполняет базу разговором; зовёт его оператор.

## Как идёт работа

`/drive` — рабочий контур: задача с критерием закрытия, шаги под проверкой, фиксация знания в базе в конце. Порядок работы задаёт `flow.md`, который проект пишет в своей базе.

Память задачи адресует рабочая копия в дереве сессии, а не ветка: **одна рабочая копия — одна задача**, вторая параллельная — второй `git worktree`, который заводит `/worktree [имя]`. Переименовать или удалить папку worktree можно, когда задача закрыта.

Что нужно от оператора, становится вопросом в разделе «Оператору» памяти и попадает в сводку сессии. Ответ оператор пишет прямо в файл; сессия, у которой вся работа ждала ответа, ждёт файл в фоне и просыпается сама.

Что стоит сделать, но не в работе, — запись в `backlog.md` базы под номером `B-N`; по номеру её и берут: `/drive B-12`. Показывает бэклог и записывает в него сказанное своими словами `/backlog`.

## Что видит сессия

Открытая в связанной копии — **знание проекта**, что именно — [reference/base-layout.md](reference/base-layout.md). С ним — имя проекта, путь базы и копии, текст [reference/invariants.md](reference/invariants.md) и пути остальных справок из [reference/](reference/).

Разошлась база с правилами кита — приходит раздел сверки с находками; чистая база его не даёт. Коммит в базу сверяется ещё раз по своим файлам: красное не проходит, похожее на секрет пропускает только оператор.

Следом — память своей копии, а нет её — адрес, по которому заводить. Память соседней копии не приезжает; брошенный файл сверка называет путём.

Нет указателя ни у репозитория, ни у связанного каталога над сессией, или каталог вне git — ничего. Стороны не сошлись — сессия получает, что разорвано и что чинить, и работу со знанием останавливает.

## Глоссарий

- **База знаний, база** — отдельный репозиторий со знанием проекта: что за система, где граница решений агента, какие решения действуют, флоу, бэклог и память задач.
- **Бэклог** — `backlog.md` базы: что стоит сделать или решить и сейчас не в работе.
- **Вобрать ответ** — перенести ответ оператора туда, где он действует, и удалить вопрос из памяти задачи.
- **Вопрос оператору** — блок в разделе «Оператору» памяти задачи: одно решение или одно действие, которое нужно от оператора, со строкой `ответ:`.
- **Выход** — чем подтверждается, что шаг флоу пройден: коммит, строка в памяти, вывод прогона.
- **Замечание** — что ревьюер кита нашёл в тексте кита.
- **Замысел** — одна правка кита, названная одной фразой.
- **Запись бэклога** — раздел `backlog.md` с номером `B-N`: одно дело.
- **Инварианты** — правила, которые действуют в каждой сессии под китом.
- **Исполнитель** — кто делает шаг флоу: оркестратор, оператор или субагент.
- **Критерий закрытия** — проверяемый признак «сделано», записанный в память задачи до работы.
- **Механизм** — файлы репозитория кита.
- **Находка** — что сверка нашла в базе не так: красная или предупреждение.
- **Основная копия** — репозиторий проекта или один его каталог, который связывают с базой.
- **Оператор** — человек, который делает то, чего агент не может: принимает необратимое решение, даёт доступ, пишет коллеге.
- **Оркестратор** — сессия `/drive`, которая ведёт флоу и пишет в базу.
- **Память задачи** — файл в `work/` базы, где рабочая копия ведёт свою задачу, пока та в работе.
- **Подача** — что хук передаёт сессии на старте.
- **Потолок** — наибольшее число строк файла базы.
- **Рабочая копия** — папка с кодом проекта, где открыта сессия: основная копия или её git worktree.
- **Рабочий контур** — ведение задачи через `/drive`: от критерия закрытия до фиксации знания.
- **Разрыв** — связь копии с базой не сошлась.
- **Решения** — файлы `decisions/` базы: как договорились делать одну область системы и почему.
- **Сведение** — проверка текста кита агентом `kit-reviewer` и правка по его замечаниям.
- **Сверка** — проверка базы на правила кита.
- **Связь** — указатель и список копий, которые сходятся.
- **Список копий** — `agents-kit.json` в корне базы: какие основные копии база числит своими.
- **Справки** — файлы `reference/` кита: правила, которые сессия читает посреди работы.
- **Стенд** — временные репозитории, на которых `check-kit.ps1` проверяет кит.
- **Тест входа** — вопрос к строке знания: убери её — начнёт ли сессия ошибаться?
- **Указатель** — ключ в локальном git config рабочей копии: где база репозитория или одного его каталога.
- **Фиксация знания** — запись в базу в конце работы того, что дорого переоткрывать.
- **Флоу** — `flow.md` базы: шаги, которыми на проекте ведут задачу от взятия до закрытия.
- **Хук** — скрипт кита, который Claude Code запускает сам.
- **Шаги работы** — строки раздела «Шаги» памяти задачи: работа внутри открытого шага флоу.

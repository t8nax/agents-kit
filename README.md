# agents-kit

Агентский кит для Claude Code: **инженерную работу ведёт агент, а оператор вступает там, где агент не может**.

Знание проекта живёт **отдельным репозиторием базы знаний**, вне кода и вне кита. Сессия находит базу по указателю в git config рабочей копии и с первой секунды получает её знание вместе с инвариантами кита.

## Как связаны основная копия и база

Связь двусторонняя, обе стороны обязательны.

| Сторона | Где лежит |
|---|---|
| указатель репозитория | `agents-kit.base` в локальном git config копии |
| указатель каталога | `agents-kit.<путь от корня>.base` там же |
| список копий | `agents-kit.json` в корне базы |

Каталогом под кит берут, например, модуль монорепы. Сессия берёт ближайший связанный каталог над собой, а нет такого — указатель репозитория.

## Установка

**Каталог автозагрузки — для того, кто кит правит.** Ссылка на `plugin` клона в `~/.claude/skills/`: кит грузится прямо из клона, без установки и без версий.

```powershell
New-Item -ItemType Junction -Path "$env:USERPROFILE\.claude\skills\agents-kit" -Target <клон кита>\plugin
```

**Маркетплейс — для того, кто китом пользуется.**

```powershell
claude plugin marketplace add <клон или github-репозиторий>
claude plugin install agents-kit@agents-kit
```

Оба способа сразу не включать.

## Обновление

**Поставленный каталогом автозагрузки** обновляется `git pull` в клоне. Правка действует со следующей сессии, а в открытой — после `/reload-plugins`; версия в этом не участвует.

**Поставленный маркетплейсом** копируется в кэш плагинов, и копия меняется только со сменой номера версии. У сторонних маркетплейсов автообновление выключено по умолчанию — включается один раз в `/plugin` → **Marketplaces** → `agents-kit`. Иначе обновление идёт руками, и маркетплейс обновляется отдельно от плагина:

```powershell
claude plugin marketplace update agents-kit
claude plugin update agents-kit@agents-kit
```

Автообновление срабатывает после старта сессии с задержкой до десяти минут: открытая сессия доигрывает на прежней версии, свежую берёт следующая.

**Что говорит номер.** Сменился средний разряд (`0.X.0`) — после обновления нужна работа руками, и в чём база разошлась с новым форматом, назовёт сверка базы в первой же сессии. Сменился последний (`0.x.Y`) — обновиться и пользоваться.

## Связать проект с базой

Сначала база — каталог рядом с рабочими копиями, вне них, с именем вида `<проект>-knowledge`:

```powershell
pwsh -NoProfile -File <клон кита>\plugin\scripts\base-init.ps1 -Path <каталог базы> -Name "<имя проекта>"
```

Скрипт раскладывает каркас с именем проекта в заголовках (без `-Name` — имя каталога) и заводит репозиторий; повторный прогон заполненного не трогает и довозит недостающее. Что за файлы — [plugin/reference/base-layout.md](plugin/reference/base-layout.md).

Дальше из основной копии:

```powershell
pwsh -NoProfile -File <клон кита>\plugin\scripts\link.ps1 -Base <каталог базы>
```

Команда пишет обе стороны и довозит субагентов базы в копию. Под кит идёт один каталог репозитория — та же команда с `-Scope Directory`, запущенная в нём. Вторая основная копия проекта связывается так же; `git worktree` связывать не нужно — он приводится к основной копии. Без аргументов скрипт показывает, как связано сейчас, и называет связанные каталоги репозитория, — первая диагностика при разрыве и при молчании кита.

`/onboard` — те же шаги из открытой в проекте сессии: скилл заводит базу, связывает копию и заполняет базу разговором; зовёт его оператор.

## Как идёт работа

`/drive` ведёт задачу: критерий закрытия, шаги под проверкой, фиксация знания в базе в конце. Порядок работы задаёт `flow.md`, который проект пишет в своей базе.

Субагентов, которых зовёт флоу, база держит у себя, а `agents-deploy.ps1` довозит их в рабочую копию мимо git проекта. Звать довезённого можно со следующей сессии.

Память задачи адресует рабочая копия в дереве сессии, а не ветка: **одна рабочая копия — одна задача**, вторая параллельная — второй `git worktree`, который заводит `/worktree [имя]`. Ненужную копию убирает `/worktree remove <путь>`: копию с живой задачей, незакоммиченной работой и основную он не трогает, а ветка после удаления остаётся.

Что нужно от оператора, становится вопросом в разделе «Оператору» памяти и попадает в сводку сессии. Ответ оператор пишет прямо в файл; сессия, у которой вся работа ждала ответа, ждёт файл в фоне и просыпается сама.

Запись в `backlog.md` базы носит номер `B-N`; по номеру её и берут: `/drive B-12`. Показывает бэклог и записывает в него сказанное своими словами `/backlog`.

## Что видит сессия

Открытая в связанной копии — **знание проекта**, что именно — [plugin/reference/base-layout.md](plugin/reference/base-layout.md). С ним — имя проекта, путь базы и копии, текст [plugin/reference/invariants.md](plugin/reference/invariants.md) и пути остальных справок из [plugin/reference/](plugin/reference/).

Разошлась база с правилами кита — приходит раздел сверки с находками; чистая база его не даёт. Коммит в базу сверяется ещё раз, прежде чем уйти в историю: красное не проходит, похожее на секрет пропускает только оператор.

Следом — память своей копии, а нет её — адрес, по которому заводить. Память соседней копии не приезжает; брошенный файл сверка называет путём.

Нет указателя ни у репозитория, ни у связанного каталога над сессией, или каталог вне git — ничего. Стороны не сошлись — сессия получает, что разорвано и что чинить, и работу со знанием останавливает.
